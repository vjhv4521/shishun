# Project Haven 策划案差异与剩余执行方案

更新日期：2026-09-23。评估对象为当前工作区的 Unity 0.2.0 源码、场景、构建产物与已有测试日志；未执行的人工双机、长时间运行和 Hosted 增量更新均标为待验收。本文件是后续执行基线，原策划案中的 4 周／20 日排期不再当作当前剩余工期。

## 一 当前结论

项目已具备可启动的主菜单、单机 `WorldGenMap` 玩法与营地管事、FishNet 局域网房间、独立的 WP4 服务端权威合作玩法样机、Gateway、HybridCLR 与 YooAsset 启动链，以及 0.2.0 Windows Offline Client。当前最大的差距不是再增加素材，而是将**原游戏交互**与**联机权威状态**接成同一套玩法：WP4 面板中的资源球、建筑标记、敌人和背包不是 SurvivalEngine 场景对象及原生 UI 的联网版本。

项目不能因本机双客户端自动冒烟通过就宣布原策划案全部完成。冒烟验证了连接、入场、一次采集同步与私人背包隔离；没有证明原生采集／建造、两台电脑、联机 AIGC 任务、Hosted 热更新或长时间稳定性。

## 二 策划内容与实际游戏的差异

| 策划案表述 | 项目中可确认的实际内容 | 修订决定 |
|---|---|---|
| 一张小岛／灾后地图、固定生存主线 | 当前入口为 `WorldGenMap`，有 WorldGenerator 和 SurvivalEngine 单机系统；没有经验证的固定小岛剧情 | 以当前地图和营地为背景，不承诺岛屿剧情或第二地图 |
| 木材、石头、食物都进入联机 MVP | 单机有物品、烹饪及面包奖励；WP4 联机只结算木材、石料、斧头和金币 | 单机保留已有食物玩法；联机第一阶段限定木／石，不将食物同步写作已完成 |
| 3～5 个制作配方、4～6 种联网建筑、Ghost 预览 | SurvivalEngine 有大量配方和建筑资源；联机权威服务只支持 `axe`、`firepit`、`wall_wood`，以面板与同步标记呈现 | 策划案采用现有配方和两类联机建筑作为基础；Ghost、箱子和更多配方列为扩展 |
| 玩家移动、动画、生命、交互完整同步 | FishNet 玩家对象及位置输入已存在；联机动画、生命、原生交互没有同等完成证据 | 分开写“已实现移动”和“待接入生命／动画／原生交互” |
| 敌人巡逻、追击、攻击及夜间防守 | WP4 服务端有一个敌人的目标选择、移动、生命、死亡与复活；未见玩家受击和夜间波次闭环 | 不以夜间守城作为当前完成条件；补玩家受击后再决定是否扩展夜袭 |
| AI NPC 自由对话并生成可变目标任务 | 单机管事能聊天，并从固定木／石委托目录选择候选、给面包和存档；WP4 联机共享任务固定为木 3、石 2，DeepSeek 只生成展示文本 | 使用“受约束候选任务＋本地回退”，不得称联机 AI 已动态决定目标或奖励 |
| 客户端验证 AI 任务 | 现有 Gateway 与规则层有白名单；联机关键结算应由服务端决定 | 修订为 Gateway 和服务端校验，客户端仅显示结果 |
| 建筑和敌人使用完整网络 Prefab | `HavenPlayer` 已注册 FishNet；WP4 建筑和敌人为快照标记，不是原建筑／敌人网络 Prefab | 完成原生对象接线之前，不写作“网络建筑对象已完成” |
| 4 周从零开发日程 | 项目已到 0.2.0 样机，原 20 日表属于历史计划 | 改为按剩余缺口和放行条件排期 |

单机营地任务的实际规则是：靠近管事，选择木材或石料委托，收集后**整单**交付，奖励面包，同日每种物资最多一次，结果进入本地存档。它与联机 WP4 的**分批贡献、两名贡献者、各得金币**是两个不同系统。策划案已经将两种模式分开描述，不应把其中一种的验收结果推到另一种。

## 四 修订后的完成范围

**必须交付的 0.2.0 完成版：** 从主菜单进入单机并完成一项营地委托；两台电脑在同一局域网创建／加入房间并看到实际玩家；原场景木／石交互经服务端结算到私人背包；制作斧头、放置火堆与木墙、击败一个敌人、两人完成共享委托并各领一次奖励；晚加入看到当前状态；断线或退出能回菜单；Gateway 失败时任务仍可完成；Hosted 热更新完成一次 V1→V2 下载和重试；客户端、原生服务器、网关与说明可在演示机复现。

**不纳入这次阻断验收：** 联机食物、箱子共享、4～6 类联机建筑、夜袭波次、自由生成任意任务、第二地图、互联网匹配、账号持久化和断线身份恢复。单机已有的这些素材或功能可以保留，但不得在联机演示时称其已权威同步。若老师明确要求其中某项，再单独增加工作量并调整排期。

## 五 分阶段执行方案

以下是**剩余工作估算**，单位为人日，按现有代码可复用且需求不再扩大估计；两人并行会缩短日历时间，但不会等比例减少总人日。合计 **23～36 人日**。若只要求展示独立 WP4 面板，而不要求原生玩法联网，可省去大部分阶段 B、C，但必须在策划案和答辩中明确“联机样机”，不能按原计划宣称玩法统一。

### A 冻结验收基线 1～2 人日

1. 保留并检查当前未提交变更，确认 0.2.0 源码与构建产物的版本对应关系；不清理他人改动。
2. 固定 Unity 6000.5.5f1、FishNet、HybridCLR、YooAsset、协议 3、UDP 7770 和 Gateway 5080；写入唯一配置说明。
3. 建立逐项验收用例与证据目录。重跑项目校验、EditMode、PlayMode、Gateway，并记录提交号、构建时间和日志。

**放行：** 工程无编译错误；版本、端口、模式边界与测试基线可追溯。

### B 原生玩法接入联机权威服务 7～10 人日

1. 列出 `WorldGenMap` 真资源点、SurvivalEngine 物品 ID 与 WP4 ID 的映射，先统一 `rock/stone`、`wood`、`axe`；避免平行背包并存。
2. 将原生点击／交互改为“发送采集意图 → 服务端读玩家位置与节点状态 → 回应并更新原背包 UI”；服务端拒绝越距、耗尽、重复请求。
3. 将原制作与建造入口接到权威命令；客户端 Ghost 只预览，服务端复核坡度、碰撞、距离、材料与数量，生成可追踪的真实建筑对象或明确的网络表现层。
4. 让双端和晚加入都能看到建筑、资源状态；退出与重新进房间不遗留旧标记。单机继续走原 SurvivalEngine 路径。
5. 隔离联机时的旧 `player.survival` 本地读写。同机双开曾出现文件共享冲突；联机权威状态不能受本地存档影响。

**放行：** 两台电脑不使用 WP4 调试按钮，直接通过场景交互完成木／石采集、斧头制作和两类建造；背包与世界状态一致，非法／重复请求没有收益。

### C 玩家与敌人可玩闭环 4～6 人日

1. 确定网络玩家表现：移动、转向、必要动画、生命和受击反馈；服务端限制异常输入，离房销毁对象。
2. 将敌人目标、攻击命中、伤害、死亡和复活放到服务端，客户端只播放表现；保留现有单机敌人逻辑不受影响。
3. 补建筑碰撞与敌人路径、玩家死亡／复活或明确的单局失败规则；晚加入读取完整状态。

**放行：** 双端看到同一敌人生命、玩家受击与死亡结果；连续游戏和重进场景不重复生成敌人或建筑。

### D AIGC 与共享任务整合 3～5 人日

1. 复用单机固定委托目录与 Gateway 白名单，但联机请求由服务端构造真实资源／时间／已完成状态；模型只能选合法候选并写对白。
2. 明确双模式奖励：单机维持面包，本次联机可维持金币；UI 和策划案分别显示。若统一奖励，须同步修改配方、背包和测试。
3. 服务端保存共享进度、贡献者与一次性奖励；重放、超时、断线、晚加入均不能复制奖励。
4. 网关无 Key、超时、非法 JSON 或未知候选时使用本地任务，验证正常在线路径与兜底路径各一次。

**放行：** 两端显示相同任务目标和进度；真实 DeepSeek 或本地兜底都能完成并发奖；客户端不能上报“已完成”。

### E 原生构建与热更新发布 3～5 人日

1. 在 Unity Hub 安装本机缺失的 Windows Dedicated Server Build Support，重建真正 Server 子目标；保留现有无图形 Player 替代产物作为开发用，不混淆命名。
2. 重新执行 HybridCLR Generate All，构建同一源码基线的 0.2.0 Offline Client、Hosted Client、Dedicated Server 和 Gateway。
3. 固定 LAN IP、补丁 URL、内容版本和端口；构建 V1 与仅改变可见热更内容的 V2，先发布内容再切换版本指针。
4. 第二台电脑验证首次启动、V1→V2 下载、失败重试及版本不匹配提示；不把本机 Offline 启动算作远端热更新通过。

**放行：** 两机使用相同协议与内容版本，原生 Server 自动监听，Hosted 更新前后可见差异且失败可恢复。

### F 全量验收与正式材料 5～8 人日

1. 双机测试：创建、加入、满员、错误地址、Host 退出、掉线、再次连接、晚加入、同时采集、同时建造、重复领奖。
2. 单机测试：从菜单入场、管事对话、木／石交付、面包奖励、存档读写与退出；联机不误用本地存档。
3. AIGC 在线／无 Key／断网／非法输出、Hosted V1/V2／断流／重试；1366×768 与 1920×1080 UI，至少 30 分钟双端稳定性。
4. 更新需求、设计、测试报告、部署、用户手册、PPT 与 6～8 分钟演示路线；为每个通过项保存构建号、日志和截图／视频。阻断或严重缺陷未关闭时不写“完成”。

**放行：** 两台电脑按说明独立复现完整路线；无未关闭阻断／严重缺陷；包内无密钥，文件清单和已知限制齐全。

## 六 顺序与工期

依赖顺序为 `A → B → C → D → E → F`。其中 D 可在 B 后半段并行开发，E 的构建脚本准备可提前进行，但 **E 的正式构建必须基于已冻结的 B/C/D 代码**；F 的用例设计从 A 开始，最终签收在 E 后。两名开发加一名兼任测试／文档人员，基础估算约 3～4 周，含第八节缓冲建议按 3～5 周日历排期；单人顺序执行基础约 5～8 周、含缓冲约 6～9 周。外部等待（安装模块、第二台电脑、真实模型账号或网络）不计入人日。

| 里程碑 | 必须提交的证据 | 未通过时的处理 |
|---|---|---|
| M0 范围冻结 | 版本表、用例清单、基线测试 | 停止追加新玩法 |
| M1 原生联机玩法 | 双机真对象交互视频、背包／建筑状态日志 | 回到 B/C 修复，不进入正式演示录制 |
| M2 AI 任务 | 在线与兜底两条任务记录、双端奖励检查 | 使用固定本地任务演示，并明确在线功能未验收 |
| M3 发布链 | 原生 Server、Hosted V1/V2、第二台电脑下载日志 | 使用 Offline 演示并声明远端热更新未完成 |
| M4 交付 | 全量测试报告、部署复现、PPT／视频／说明 | 不标记项目最终完成 |

## 七 现在即可执行的第一步

先完成 A，并在两台电脑上做一次**不改代码**的现状试运行：一台运行现有无图形服务器替代产物，另一台运行 0.2.0 Offline Client；按 `doc/08_WP4_联机玩法同步说明.md` 验证当前样机。记录可见窗口的菜单、管事、WP4 面板与异常日志，然后冻结 B 阶段要接入的真实交互清单。这一步会把“代码存在”和“玩家实际可用”分开，避免在后续计划里继续混写。

## 八 2026-09-23 再核对：离新策划案到底差多少

这里的“完成”指**同一发布候选构建在两台电脑上按策划案操作并留证**，不是仓库里有类、Prefab 或测试。当前没有足够证据给出可信的百分比；用“已实现／样机／缺失／未验收”和剩余人日更准确。

## 十 放行门槛与停工线

1. **M0 基线放行：**源码、版本、配置、测试用例和当前失败清单齐全；否则不开始覆盖旧资源或改协议。
2. **M1 可玩放行：**两台电脑不用 WP4 调试按钮，从原场景完成采木、采石、制斧、放火堆／木墙；敌人可伤玩家，单机回归通过。只有面板样机则停在 M1，不进入“完成版”演示。
3. **M2 任务放行：**联机候选与奖励由服务端决定；真实在线和回退都能在两机结算；重连／晚加入／重放不能领两次。失败则只可声明固定任务回退已通过。
4. **M3 发布放行：**同源 0.2.0 专服、Hosted V1／V2 和 Gateway 可部署，第二台电脑完成下载与重试；仅有无图形替代服或 Offline 包不能签收。
5. **M4 最终放行：**发布候选版自动测试、全部 P0 双机用例、30 分钟稳定性、用户手册和答辩材料齐全，未关闭的阻断／严重缺陷为零。每个放行决定附日期、构建号、负责人和证据路径。

若第二台电脑、Dedicated Server 模块或 DeepSeek 服务一时不可用，可以继续做与之无关的 B／C 测试和文档，但对应 M2／M3／M4 保持“待验收”，不通过改措辞将其计为完成。计划范围外的夜袭、联机食物／箱子和任意任务生成，需要单独评估并另加人日。
